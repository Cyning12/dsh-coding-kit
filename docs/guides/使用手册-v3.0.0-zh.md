## 1. 这是什么

**SpecWave** 是一个**多宿主编码 CLI**：用**单一声明式适配表**把「规范入口」物化到 13 个宿主（Cursor · Claude Code · 可选 DSH · agents · Copilot · Codex · Windsurf · Gemini CLI · opencode · Roo Code · Zed · Cline · aider）的原生落点，并提供一套**机械门禁**与 **Harness 过程命令**。

一句话记住它的定位：

> **闸的真值是终端 CLI 的退出码，不是聊天里说"我觉得通过了"。**

### 1.1 三个核心承诺

| 承诺 | 含义 |
|------|------|
| **门禁随包内置** | `check` / `verify` / `gate-check` / `audit` 的判定在 **CLI 进程内**完成，**不依赖**宿主是否真的执行了 hook |
| **failClosed** | P0 门禁失败一律 **exit 2**；CI 与 Agent 必须把 2 当**硬停** |
| **零行为变更的拆分** | 3.0.0 对 `src/` 做了大重构（god-file 拆分），但**对外可达面不变**（`exports` 只开 3 个入口，`lib/*` 子路径全部封死） |

### 1.2 ⚠️ 不该期待什么（诚实边界）

以下**尚未实现**，请勿对外声称（口径真值源：`assets/harness/claims-boundary.yaml`，机检 `scripts/check-claims.mjs`）：

| 不要声称 | 正确说法 |
|---------|---------|
| 「接入即获得 L3」 | 无 hook 机制的宿主**显式降级 L1+L2** |
| 「13 宿主全部有 hook 拦截」 | **config-hook 3 宿主**；shell-hook = git 层宿主中立；其余显式降级 |
| 「门禁靠宿主 hook 强制」 | 门禁靠 **CLI 进程内判定**（`exit 2`）；hook 只是分发入口 |
| pre-archive 宿主内真实触发 | 仅 fixture + `host verify` 兜底（**规划中**） |
| catalog 远程在线分发 / npm provenance | **规划中 / 未启用** |

> 〔截图占位 · S-01〕**术语表首页**
> - **画面**：浏览器或编辑器打开仓根 `GLOSSARY.md`，滚动到「简体中文 → 帽制（hat）」小节，可见 `task.md` / `Harness` / `hat` / `kit-*` / 门禁五组术语。

## 3. 五分钟上手

### 3.1 路径 A · Cursor（最常用）

```bash
cd your-repo
git init                      # 若还不是 git 仓（verify 有 git-root 归属校验）

# ① 只读校验适配表
npx spec-wave@3.1.0 host validate
# 期望：HOST VALIDATE: PASS · exit 0

# ② 先 dry-run 看要写什么（零写入）
npx spec-wave@3.1.0 host apply --tools cursor --profile core

# ③ 确认无误再写盘
npx spec-wave@3.1.0 host apply --tools cursor --profile core --yes
# 期望：HOST APPLY: PASS · exit 0

# ④ 核对物化产物与声明一致
npx spec-wave@3.1.0 host verify --tools cursor
# 期望：HOST VERIFY: PASS
```

写盘后，Cursor 命令面板（⌘/Ctrl+Shift+P）搜 `kit-` 应可见：

```
kit-verify · kit-gate-status · kit-hat-reanchor · kit-init-guide · kit-apply-standards
```

> 〔截图占位 · S-03〕**Cursor 命令面板里的 kit-***
> - **画面**：Cursor 打开 demo 仓，命令面板输入 `kit-`，下拉列出 5 条 `kit-*` 命令。
> - **验证点**：5 条齐全；点开 `kit-verify` 后正文是 **POINTER**（指向 `npx spec-wave verify`），不是 L1 全文。
> - **注意**：`kit-verify` 正文必须让读者看到 **exit 0/1/2 的语义**，禁止口头宣称闸过。

> 〔录屏占位 · R-01〕**host apply 端到端（约 90s）**
> - **镜头 1（0-20s）**：`mktemp -d` 建干净 demo 仓 → `git init` → `pwd` 念出路径（证明不是 kit 源码仓）。
> - **镜头 2（20-45s）**：`host validate` → PASS；`host apply`（无 `--yes`）→ 念出 planned 列表；`ls -a` 证明 `.cursor` 与 `CLAUDE.md` **都还不存在**（dry-run 零写入）。
> - **镜头 3（45-75s）**：`host apply --yes` → PASS；`ls .cursor/commands/` 与 `head CLAUDE.md` 展示真实产物。
> - **镜头 4（75-90s）**：`host verify` → PASS；口播「verify 校验的是物化产物与声明是否一致，篡改会报红 exit 2」。

```bash
npx spec-wave@3.1.0 host apply --tools claude --profile core --yes
```

产物：

- `.claude/commands/kit/<verb>.md` → Claude Code 里表现为 **`/kit:verify`** 等
- `.claude/skills/harness-*`
- `.claude/settings.json`（config-hook 落点）

> **local 块永不覆写**：`<!-- cyning-harness-local:begin -->` … `end` 之间的内容，再次 apply 也不会被改动。

> 〔截图占位 · S-04〕**Claude Code slash 列表**

> - **验证点**：命名空间是 `/kit:`（不是 `/kit-`）。

### 3.3 路径 C · CI / 非交互（只做过程根，不物化）

```bash
# CI 里必须显式给 --tools（非 TTY 无值 → exit 1）
npx spec-wave@3.1.0 init --preset harness-only --tools none --yes

# 然后跑门禁（CI 的硬停点）
npx spec-wave@3.1.0 verify --task docs/tasks/active/task_<slug>.md

# 可选下一步（图谱入手 · 可审草稿，非已签收真值；见 §10）
npx spec-wave graph scaffold
# 默认 dry-run；确认后加 --yes 写盘 docs/_tech_graph/ + REVIEW_CHECKLIST.md
# 勿称「自动权威图谱」；HG-GRAPH-MODULES 须人签
```

> `check` **恒 exit 0**（只给版本建议）；真正的阻断点是 `verify` / `gate-check` / `audit` 的 **exit 2**。  
> `init` **不**捆绑生成 `_tech_graph`；上列 scaffold 仅为 quickstart **文案下一步**（与 `INIT_QUICKSTART` 第 4 步同口径）。

## 4. 核心对象

Harness 过程围绕**两个文件级对象**运转。`verify --task` / `gate-check --task` / `task close` 都作用于第一个。

### 4.1 `task.md` —— 一个可执行、可验收的工作单元

**是什么**：一个 Markdown 文件描述一个工作单元（背景/目标 · 范围 · 非范围 · 失败路径 · 验收标准 · Harness 元信息 · 人工闸表）。

**关键约束**：闸表中 `HG-AUDIT-R1` 必须为 `approved`，**帽 30 才可改码**。

**从哪来**：`npx spec-wave sync prompts --yes` 会把 `docs/harness/templates/TASK_TEMPLATE.md` 物化到你的仓。**CLI 永不主动向 `docs/tasks/` 写示例 task**——是否落文件永远由你显式执行。

**放哪**：
- 在途：`docs/tasks/active/task_<slug>.md`
- 归档：`npx spec-wave task close --file <task> --yes` → `docs/tasks/done/`

最小骨架：

```markdown
# Task：加登录限流

> **状态**：`draft`

## Harness 元信息
| 字段 | 值 |
|------|-----|
| **task_slug** | `login-rate-limit` |
| **test_strategy** | `required` |
| **wiki_delta** | `none` |

### 人工闸
| human_gate_id | status | blocks_hats | 说明 |
|---------------|--------|-------------|------|
| HG-AUDIT-R1 | pending | 30 | 22 R1 落盘后人签 |

## 范围 / ## 非范围 / ## 失败路径 / ## 验收标准
（逐节照模板填写；**验收须含可跑命令**）
```

> ⚠️ **闸表必须是 4 列**（末尾要有 `说明` 列）。解析器要求 **4 个单元格**；写成 3 列会被**静默忽略**（闸表解析为空）——此时即使你把 `HG-AUDIT-R1` 填成 `approved`，`gate-check` 仍会阻断，并给出**误导性理由**「HG-AUDIT-R1 非 approved」（状态列渲染为 `?`）。已实测：3 列 + `approved` ⇒ `may_start_30=false`、`gate-check` **rc=2**；补上第 4 列后同内容 ⇒ `may_start_30=true`、**rc=0**。
>
> ⚠️ **另一个会静默失效的写法：`human_gate_id` 单元格中间不要加粗体 `**`**。解析器的 id 捕获组**排除 `*`**，所以：
> - `| **HG-AUDIT-R1** | pending | 30 | 说明 |` → ✅ 能解析（`**` 只是**包裹**整个 id）
> - `| HG-AUDIT-R1（**条件闸**） | pending | 30 | 说明 |` → ❌ **整行失效**（id 格**内嵌** `**`）
>
> 判据：**id 单元格里除了最外层的一对 `**` 之外，不要再出现 `*`**。若闸行莫名"不生效"，先数一下 id 格里有没有多余的 `*`。
>
> **最稳做法：直接复制 `docs/harness/templates/TASK_TEMPLATE.md`**（随包模板已是 4 列）。

### 4.2 `spec.md` —— task 回溯的需求规格

已签的需求规格。task 通过「关联 SPEC」引用它。

```bash
npx spec-wave verify --spec docs/spec/<主题>/<SPEC>.md
# 闸：实现前须已有书面审查
```

放在 `docs/spec/`（本仓按主题分目录）——**CLI 不物化 spec 文件**，由你或你的 Agent 撰写。

### 4.3 帽制（hat system）

| 帽 | 角色 | 干什么 |
|----|------|--------|
| **00** | 委派 | 只分派，不写码 |
| **10** | 规格 / 任务 | 写 `spec.md` / `task.md` |
| **20** | 审查 | 审规格、审任务（产出审查文） |
| **30** | 执行 | **改码**（前置：`HG-AUDIT-R1=approved`） |
| **40** | 自检 | 自查 |
| **50** | 收口 | 归档 |

> **注意**：默认**不物化 30/40** 的 skill（`harness-30-*` / `harness-40-*` 不进默认分发）——执行仍须过 `verify`。

### 4.4 人工闸（human gate）

task 里的 `### 人工闸` 表是 `verify` 的**判定真值**。

| 闸 ID 示例 | 常态 | blocks_hats |
|-----------|------|-------------|
| `HG-AUDIT-R1` | `approved` 后 30 才可改码 | 30 |
| `HG-SCHEMA-CHANGE` | schema/契约变更前的人工裁决 | 依声明 |

**3.0.0 的关键变化（闸判定泛化）**：闸判定不再硬编码 3 个 ID，而是**声明式全闸扫描**——你在闸表里声明的任意 `HG-*` 行都会被读取与判定，`blocks_hats` 列决定它挡哪一顶帽。

> 〔截图占位 · S-05〕**task.md 的人工闸表**
> - **画面**：编辑器打开一个真实 `docs/tasks/active/task_*.md`，高亮 `## Harness 元信息` 与 `### 人工闸` 两节。
> - **验证点**：能看到 `HG-AUDIT-R1 | approved | 30` 一行；旁边 `status` 是 `approved` 而非 `pending`。

## 5. 初始化项目骨架

### 5.1 `init`

```bash
npx spec-wave@3.1.0 init --preset harness-only --tools cursor,claude,dsh --yes
```

| 参数 | 语义 |
|------|------|
| `--preset harness-only` | **唯一合法值**（NAME 词表） |
| `--tools all \| none \| LIST` | `LIST` 如 `cursor,claude,dsh`；`all` = 适配表全部；`none` = **只建过程根、不物化** |
| `--profile core \| expanded` | `core` 默认；`expanded` 追加 `kit-hat-*` 薄壳 |
| `--host-adapt` / `--no-host-adapt` | `--no-host-adapt` 既不 apply **也不写粘性** |
| `--target PATH` | 目标仓根 |

成功后 stdout 打印 quickstart（含第 4 步真实命令 `npx spec-wave graph scaffold`）：生成 `docs/_tech_graph/` **可审草稿**（默认 dry-run；`--yes` 写盘），**不是**已签收架构真值。细节与命令面见 **§10**；`init` 本身**不**写盘图谱。

**TTY vs 非 TTY**：
- TTY 且无 `--tools` → **交互询问**（多选 / all / none）
- 非 TTY / CI 且无 `--tools` → **exit 1**（必须显式）

### 5.2 `sync prompts`

```bash
npx spec-wave@3.1.0 sync prompts --yes
```

物化 **11 个** prompt 文件 + `docs/harness/templates/TASK_TEMPLATE.md`。

> **默认 dry-run**；本地内容与包内不同 → 列为 `conflict` 且**不覆盖**（`--force` 才覆盖）。

**不覆盖的 S2 过程域**（真值源唯一，`S2_TRUTH_PREFIXES`）：
`docs/tasks/` · `docs/harness/reviews/` · `docs/harness/invokes/by-task/`（以及 legacy 裸 `reviews/` / `invokes/by-task/`）。

### 5.3 目录布局（记住这三个）

```
your-repo/
├── .coding-kit/              # 过程落盘现行根（manifest / host-tools.json 粘性 / backups）
│   └── host-tools.json       #   已选宿主粘性（host_ids + profile）
├── docs/
│   ├── tasks/active|done/    # S2 · task 文件
│   ├── spec/<主题>/          # 需求规格
│   └── harness/
│       ├── templates/        # TASK_TEMPLATE.md
│       ├── prompts/          # 11 个 prompt
│       ├── reviews/          # S2 · 审查文
│       └── invokes/by-task/  # S2 · 留证
└── .cursor/ .claude/ .dsh/   # 宿主物化落点（由 host apply 写）
```

> `.cyning-harness/` 是 **legacy 只读**——勿再当新标准目录。

## 6. 多宿主物化

### 6.1 命令四件套

| 命令 | 作用 | 关键语义 |
|------|------|---------|
| `host validate` | 只读校验适配表 | 契约不匹配 → **exit 2 零写入** |
| `host apply` | 写盘物化 | **必须**带 `--tools`；无 `--yes` = dry-run |
| `host update` | 刷新产品 commands/skills | 解析序：CLI `--tools` → 粘性 → 否则 **exit 1**；`conflict` 默认不覆盖（`--force` 才覆盖） |
| `host verify` | 校验物化产物 vs 声明 | 篡改/删除 → 报红 **exit 2**（fail-closed） |

### 6.2 粘性（sticky）

`--yes` 成功写盘后更新 `.coding-kit/host-tools.json`：

```json
{ "version": 1,
  "host_ids": ["cursor", "claude"],
  "profile": "core",
  "updated_at": "2026-09-18T01:23:51.373Z",
  "kit_semver": "3.1.0" }
```

之后升包刷新**不必再抄 `--tools`**：

```bash
npx spec-wave@3.1.0 host update --yes     # 只刷已选宿主
```

> **dry-run 不写粘性**。

### 6.3 13 宿主落点矩阵（profile `core`）

## 7. 门禁链路与 hooks

### 7.1 三层闸（L1 / L2 / L3）

| 层 | 位置 | 是否总可用 |
|----|------|-----------|
| **L1** | prompt 模板（把纪律写进喂给模型的上下文） | ✅ 总可用 |
| **L2** | CI 流水线（`verify` / `gate-check` 的 exit 2 硬停） | ✅ 总可用 |
| **L3** | 宿主运行时 hook（提交/归档时自动触发） | ⚠️ **仅当宿主暴露可钩机制** |

**降到 L1+L2 时必须显式降级并输出可区分**——不允许"静默 no-op 假装有 L3"。

### 7.2 hooks 三态机制

适配表 `surfaces.hooks.mechanism` 三态：

| mechanism | 含义 | 典型宿主 |
|-----------|------|---------|
| `config-hook` | 宿主配置文件里挂钩子 | Cursor（`.cursor/hooks.json`）· Claude Code（`.claude/settings.json`）· Gemini CLI（`.gemini/settings.json`） |
| `shell-hook` | git 层钩子（**宿主中立**） | 任何用 git 的仓 |
| `none` | **无机制 → 显式降级 L1+L2** | 其余宿主（含 DSH 等） |

> ⚠️ **自定义宿主（B5）只能 `mechanism: none`**：`config-hook` 的落点映射表**仅覆盖内置 3 宿主**（`claude` / `cursor` / `gemini` · 真值 `CONFIG_HOOK_HOSTS` · **不扩表**）。非映射表宿主若声明 `config-hook`，`host validate` 会 **PASS + WARN**（stderr / `--json#warnings` · exit 0 不变），但 `host apply` 会 **fail-closed exit 2** 并点名：
> ```
> host apply: config-hook 宿主无物化落点映射: acme-ai（族映射表外宿主 fail-closed · 不静默）
> ```
> 即**自定义宿主只能拿到 L1+L2**（不自动获得 L3）——这是设计边界，非缺陷。想加自定义宿主时请用 `mechanism: none`。

实际物化样例（Cursor）：

```json
{ "version": 1,
  "hooks": { "beforeShellExecution": [
    { "command": "npx spec-wave hook-guard --trigger pre-commit" },
    { "command": "npx spec-wave hook-guard --trigger pre-archive" } ] } }
```

### 7.3 `hook-guard` —— 宿主 hook 的门禁分发

```bash
npx spec-wave hook-guard --trigger pre-commit
npx spec-wave hook-guard --trigger pre-archive
npx spec-wave hook-guard --trigger pre-commit --command 'npx spec-wave@3.1.0 verify --task <task>'
```

**真跑语义**（本机实测）：

| 调用 | 退出码 |
|------|--------|
| `--command 'true'` | **0**（门禁绿 → 放行） |
| `--command 'false'` | **2**（门禁红 → 阻断） |
| 无 `--command`（用默认门禁命令） | 门禁失败即 **2** |

> **实践建议**：默认门禁命令会去调 `npx spec-wave …`。**离线 / 沙箱 CI** 里这会导致取包失败 → fail-closed 阻断（宁拦不放，语义安全）。若你对 CI 的**确定性**有要求，任选其一：
> 1. **预热 npm 缓存**（CI 步骤先 `npm install` / 缓存 `~/.npm`，保证 `npx` 可离线命中）；或
> 2. **物化时钉版**（**实验性 · 缺省关闭** · 不改无旗标默认物化字节）：
>    ```bash
>    npx spec-wave host apply --tools cursor,claude --yes --pin-hook-version
>    # 或显式：--pin-hook-version=3.1.0
>    ```
> 3. **运行时用 `--command` 显式钉版本**：
>    ```bash
>    npx spec-wave hook-guard --trigger pre-commit --command 'npx spec-wave@3.1.0 verify'
>    ```

> 〔截图占位 · S-07〕**hook-guard 红绿对照**
> - **画面**：一张终端并排图 —— 左半 `hook-guard --command 'true'` → 绿色 `rc=0`；右半 `hook-guard --command 'false'` → 红色 `rc=2` + "门禁红 · 阻断 pre-commit"。
> - **验证点**：两个退出码清晰可读。

## 8. 校验与门禁命令

### 8.1 退出码契约（**背下来**）

| 码 | 含义 | 命令 |
|----|------|------|
| **0** | 通过 / 仅信息 | `check` **恒为 0** |

### 8.3 D5 测试制品探测（`test_strategy=required` 时）

### 13.2 2.x → 3.0.0（host-adapt 适配表 schema v1 → v2）

> **这是 3.0.0 唯一的 Breaking 项，但它对绝大多数人是"什么都不用做"。**

#### ① 默认路径：什么都不用做

- **`--file` 用旧格式适配表的消费者**：**零改动**。无 `schema_version` 键即按 v1 旧扁平语义解析（缺省 = v1）。
- **仅用内置 13 宿主的消费者**：`host validate/apply/update` 的**既有落点不变**；内置表已升级为 v2，因此 `host apply` 会**额外新增 2 件 hooks 物化**（`.cursor/hooks.json` / `.claude/settings.json`）——这是 W2 的 **additive 新能力**，不是破坏。

> **本手册的独立实测保证**（对照实验，2026-09-18）：
> 用 **v2.4.1** 与 **3.0.0 + v2.4.1 旧表** 分别物化到两个干净仓，再递归 diff：
> **全部 38 件宿主物化文件字节级相同**，唯一差异是 `.coding-kit/host-tools.json` 里的 `updated_at` 时间戳与 `kit_semver` 版本戳。
> ⇒ 「v1 表面逐字锁 · 旧表零改动」**经对照实验证实**，非自述。

#### ② 自定义表作者：想用新能力时（可选迁移）

1. 表首加 `schema_version: 2`（**整数**，不复用 `version` 字符串字段）
2. **可选**：把重复的 `verify` / `skills` 提入根级 `defaults`，或用行级 `extends`（合并语义：标量子覆盖父 · 对象逐键深合并 · **数组整体替换**）
3. **必做**：声明根级 `command_sets`（v2 表缺此节 **fail-closed**；`core`/`expanded` 非空数组）
4. **可选**：声明 `surfaces.hooks`（`mechanism` + `triggers` + `command`）

#### ③ 禁止事项

- 不要手写 `schema_version` > 2（**fail-closed 拒**，点名「未知 schema_version」，不会静默按旧格式解析）
- 不要在 `command_sets.core`/`expanded` 含 `kit-30` / `kit-publish`（内建禁词机检拒）

#### ④ `refresh-ide-blocks`（存量 IDE 块旧命令刷写）

旧包时代嵌在 marker 块里的旧命令字面可以机械刷写：

```bash
npx spec-wave refresh-ide-blocks --dry-run   # 默认即 dry-run
npx spec-wave refresh-ide-blocks --yes       # 才写盘
```

- **发现面（冻结白名单）**：仓根 `AGENTS.md` · `CLAUDE.md` · `.cursor/rules/*.mdc`（单层）
- **preflight（`--yes` 专用）**：git 脏树（**untracked 也算脏**）/ 单文件新旧混杂 / marker 配对畸形 → **exit 2 零写入**
- **备份**：`.coding-kit/backups/refresh-ide-blocks/<UTCts>/`（保留最近 5 代）
- **幂等**：刷过再跑命中 0，字节不变，exit 0

> **给存量仓 Agent 的可复制 Prompt**：见 `README.zh-CN.md`「可复制 Prompt（给存量仓 Agent）」节。

> 〔录屏占位 · R-03〕**2.x 仓升级到 3.0.0（约 120s）**
> - **镜头 1（0-30s）**：`git worktree add` 检出 v2.4.1 → 显示旧适配表**没有** `schema_version` 键。
> - **镜头 2（30-60s）**：用 3.0.0 的 CLI 对**同一张旧表**跑 `host validate --file` → **PASS**（念：旧表零改动可读）。
> - **镜头 3（60-100s）**：分别物化到两个干净仓 → `diff -r` → 唯一差异是 `host-tools.json` 的版本戳。
> - **镜头 4（100-120s）**：`host update --yes` 刷粘性 → `host verify` → PASS。
> - **口播**：「升级的痛点被压到几乎为零——旧表原样跑，想用新能力再加一行 `schema_version: 2`。」

## 14. 排障 FAQ

| # | 症状 | 原因 / 处置 |
|---|------|------------|
| 1 | `host update` 报 **exit 1** | 缺 `--tools` **且**无粘性。先 `host apply --tools … --yes` 建粘性 |
| 2 | `host apply` 报用法错误 | `host apply` **必须**带 `--tools`（`init` 才可省） |
| 3 | `verify` 报 BLOCKED | 看是否 `HG-AUDIT-R1` 仍 `pending`；帽 30 前必须 `approved` |
| 4 | D5 报「无测试制品」exit 2 | 仓内补强信号：`tests/` 目录、`*.test.ts`、或含 test 步骤的 CI |
| 5 | `host verify` 报红 | 产物被改/删。`host update --tools … --yes --force` 恢复 |
| 6 | hooks 没拦住提交 | 该宿主 `mechanism` 可能是 `none`（**显式降级 L1+L2** 是设计，不是 bug）。查 `host catalog list` |
| 7 | CI 里 hook 报门禁红但本地绿 | 默认门禁命令取 `npx spec-wave` 需联网；用 `--command` 钉版 + 预热缓存 |
| 8 | Cursor 看不到 `kit-*` | 命令是**项目级**：确认在仓根 apply，且 Cursor 打开的是该项目根 |
| 9 | `CLAUDE.md` 里我加的东西没了 | 你的内容应在 `<!-- cyning-harness-local:begin -->` 块内（apply 不覆写 local 块） |
| 10 | 想直接用旧版 | `npx spec-wave@2.4.2 …`；但 3.0.0 对旧表**零改动兼容**，没有停在 2.x 的必要 |
| 11 | pnpm 装不上 | `auto-install-peers=false` |
| 12 | IDE 报 `cordis.patch.yml` 缺 `op`/`path` | **误报**（yaml-language-server 把它当 RFC6902）。该文件必须保持 `- insert`，勿改 |
| 13 | 用 `--file` 自定义表 `apply` 后，不带 `--file` 跑 `host verify` 报 `hooks.json`/`settings.json` **missing** → exit 2 | **已知 3.0.0 兼容性误报**（粘性不记表源）。**处置：`verify` 与 `apply` 带同一 `--file`**；或重新 `apply`（内置表路径）。未漏检真实篡改 |

> ⚠️ **FAQ #13 详解**（`--file` 用户必读）：`host apply --file <表>` 之后，`host verify` **必须带同一 `--file`**。否则 verify 缺省走**内置 v2 表**，会期望 2 件 hooks 落点（`.cursor/hooks.json` / `.claude/settings.json`），而你的旧/自定义表**本就不会物化**它们 ⇒ 得到**误报 exit 2**。
> ```bash
> # 正确：三处带同一张表
> npx spec-wave host validate --file my-hosts.yaml
> npx spec-wave host apply --tools cursor --file my-hosts.yaml --yes
> npx spec-wave host verify --tools cursor --file my-hosts.yaml     # ← 别漏
> ```
